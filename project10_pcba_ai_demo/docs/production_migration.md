# 从 M5 Demo 到工业产线 — 5 阶段迁移指南

> Demo 证明可行性 | 产线需要系统性工程 | 总迁移周期: 4~8 周

---

## 迁移全景

```
M5 Demo                    工业产线                    周期
───────                    ────────                   ────
① 数据适配    ────────→   真实产线数据                 1~2 周
② 模型迁移    ────────→   边缘推理部署                 1~2 周
③ 服务升级    ────────→   生产级推理服务               1 周
④ 系统集成    ────────→   MES/产线对接                 1~2 周
⑤ 运维保障    ────────→   7×24 稳定运行                持续
```

---

## 阶段一：数据适配 (预计 1~2 周)

### 与 Demo 的差异

| 项 | Demo | 产线 | 差异 |
|----|------|------|------|
| 数据来源 | PKU 公开数据集 | AOI 机台 / 工业相机 | 光照/背景/分辨率差异大 |
| 缺陷类别 | 6 类通用缺陷 | 工厂实际 10~20 类 | 需重新定义分类体系 |
| 标注 | 已有标注 | 需自行标注 | Label Studio / CVAT |
| 数据量 | ~1 万张 | 至少 3~5 万张 | 工业场景更复杂 |

### AOI 机台数据对接

```
情况 A: AOI 支持图像导出 (理想)
  → FTP/SMB 共享 → Python 定时采集 → 自动入训练集

情况 B: AOI 不支持导出
  → B1: 加装工业相机 (硬件 ¥2-5K/台)
  → B2: 升级 AOI 软件 (License 费用)

情况 C: 新机台采购
  → 采购时写入 RFP: 支持图像导出 + SECS/GEM 接口
```

### 迁移学习路径

```
Demo 模型 (公开集预训练)
    ↓
冻结 backbone (通用特征已学会)
    ↓
替换检测头 (类别数 6 → 工厂实际 N 类)
    ↓
产线数据 fine-tune 50~100 epochs
    ↓
产线模型 v1 → 验证 → 部署
```

## 阶段二：模型迁移到边缘设备 (1~2 周)

### ONNX → TensorRT 转换

```bash
# 在 Jetson 上执行 (非 M5)
trtexec --onnx=best.onnx --saveEngine=best_fp16.engine \
  --workspace=1024 --fp16
```

### INT8 校准

```
校准数据: 500~1000 张代表性产线图像
不需要标注 (仅做统计分布计算)
校准时间: 5~15 分钟
```

### 推理服务切换

| 维度 | Demo (M5) | 产线 (Jetson) |
|------|-----------|---------------|
| 框架 | ONNX Runtime | TensorRT C++/Python |
| 加载 | ort.InferenceSession() | trt.Runtime.deserialize_cuda_engine() |
| 预处理 | PIL + NumPy (CPU) | CUDA GPU 预处理 |
| 批处理 | 单张 | Dynamic Batching |

## 阶段三：推理服务升级到生产级 (1 周)

| 对比 | Demo FastAPI | 产线服务 |
|------|-------------|---------|
| 框架 | FastAPI + uvicorn | Triton Inference Server |
| 负载 | 单用户串行 | 多客户端并发 |
| 模型切换 | 手动改代码 | API 热加载，零停机 |
| 健康检查 | 无 | 自动探活 |
| 请求队列 | 无 | Kafka / RabbitMQ 缓冲 |
| 错误处理 | try-except | 重试 + 降级 + 熔断 |
| 日志 | print | 结构化 JSON + ELK |

### 生产级架构

```
工业相机 (RTSP)
    ↓
DeepStream Pipeline (解码+预处理)
    ↓
Triton Inference Server (多模型+动态batch)
    ↓
业务逻辑层 (FastAPI) → MES/QMS
    ↓
Prometheus + Grafana (监控)
```

## 阶段五：运维保障 (持续)

### 关键机制

```
模型热切换:
  新版本加载到内存 → 原子切换 → 旧版本处理完当前请求后释放

断网续传:
  网络断 → 本地 SQLite 缓存 → 恢复后自动补传 → 幂等去重

健康检查:
  每 10s 探活 → GPU 显存泄漏检测 → 异常自动重启

主备切换:
  主节点故障 → 3s 内切换到备节点 → 业务无感知

模型迭代闭环:
  产线运行 → 收集误判样本 → 人工标注 → 加入训练集 → 重新训练 → 灰度发布
  周期: 每周/双周迭代
```

## 系统差异总结

| 维度 | M5 Demo | 工业产线 | 迁移工作 |
|------|---------|---------|---------|
| 数据 | 公开数据集 6 类 | 产线数据 10~20 类 | 1~2 周 |
| 模型 | .pt → ONNX | ONNX → TensorRT | 2~3 天 |
| 推理框架 | ONNX Runtime | TensorRT + Triton | 3~5 天 |
| 视频输入 | 图片上传 | RTSP 多路流 | 1 周 |
| 服务框架 | FastAPI 单进程 | Triton + 队列 | 1 周 |
| 可靠性 | 无 | 99%+ SLA | 1 周 |
| 系统集成 | 独立运行 | MES 全对接 | 1~2 周 |
| 监控运维 | 无 | Grafana + 告警 | 3~5 天 |
| 安全 | 无认证 | RBAC + 审计 + 加密 | 3~5 天 |
| **总计** | — | — | **4~8 周** |
